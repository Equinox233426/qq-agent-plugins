# 视频与动图识读（video-watch）

让机器人真的能看懂群里发的**视频**和**动图（GIF）**。

## 它解决什么问题

视觉模型只能看**单张静态图**。给它一个视频，它只知道"这是一条视频"，说不出内容。

市面上常见的做法是"均匀抽 6 帧"，但这个做法有硬伤：

- 48 秒视频取 6 帧 = 每 8 秒一个采样点
- 中间 8 秒的黑屏、转场、关键动作**全在缝里**
- 模型拿到 6 张互不相干的图，只能说"似乎是……"，然后开始编

本技能换了个思路：**分层观看**，跟你自己看视频的方式一样。

## 怎么工作

```
第一步  速览                    第二步  细看
┌─────────────┐              ┌─────────┐
│ 1  2  3  4  5│              │ 1  2  3 │
│ 6  7  8  9 10│   ──→        │ 4  5  6 │
│11 12 13 14 15│   看不清某段   │ 7  8  9 │
│16 17 18 19 20│   就放大看     └─────────┘
│21 22 23 24 25│              单格大 3 倍
└─────────────┘              能看清表情/文字
 一张图看全片
 每格带帧号
```

**速览**把全片压成一张 5×5 联络表。这不是"抽 25 帧"，是**把全片铺成一张可以一次看完的整体**——每格都带帧号，模型能指着第 13 格说"这里出现了 PPT 标题"。

**细看**针对说不清的那几秒，用更少的格数换更大的单格。

| | 速览 | 细看 |
|---|---|---|
| 帧数 | 25（5×5） | 9（3×3） |
| 覆盖 | 全片 | 你指定的时间段 |
| 单格大小 | 小 | 大 3 倍 |
| 用途 | 建立整体印象 | 看清动作/表情/文字 |

## 四个工具

| 工具 | 干什么 | 什么时候用 |
|---|---|---|
| `overview` | 铺成全片联络表 | **第一步，几乎总是先调它** |
| `zoom` | 指定时间段放大看 | 速览图上某几秒看不清时 |
| `read_text` | 读某一秒画面里的字 | 需要准确引用 PPT/字幕内容时 |
| `doctor` | 检查依赖装好没 | 铺图失败、或用户问"为什么看不了" |

## 五个能力（核心也会用）

本技能除了给模型四个工具，还向外提供五个**能力**，其中两个是给核心 `VideoReader` 用的：

| 能力 | 谁用 | 作用 |
|---|---|---|
| `video.watch` | 本技能的调用方 | 铺联络表 |
| `video.watch.available` | 同上 | 依赖体检 |
| **`video.frames`** | **核心 `VideoReader`** | **抽散帧（兼容 old API）** |
| **`video.frames.available`** | **核心 `VideoReader`** | **抽帧可用性** |
| `video.fetch-fallback` | 本技能 | 兜底下载视频 |

### 为什么必须有 `video.frames`

核心 `src/video-reader.js` 只知道 `video.frames` 这个名字（那是 frame-detective 的接口），**它不知道 `video.watch` 存在**。

所以如果 `video.frames` 没人提供，核心会判 `framesOk = false`，降级成 `route='meta'`，只给模型一句"视频信息：时长 30 秒，480×852"，**一帧画面都不给**。

这正是 2026-10-18 那次真实故障的第一层原因。

## 依赖

必需：

| 依赖 | 说明 |
|---|---|
| **Python 3.8+** | 主链路只用标准库 |
| **ffmpeg**（完整构建 ≥5.1） | 需要 `tile` `drawtext` `scdet` `freezedetect` `silencedetect` `tblend` `signalstats` 滤镜 |
| **ImageMagick** 6.x / 7.x | 拼贴图版 |
| **vw.py** | 量测与铺图的核心脚本 |

可选：

| 依赖 | 用途 | 不装的后果 |
|---|---|---|
| Pillow | **动图（GIF）通道** | 动图铺不出来，会报错提示装 Pillow |
| numpy | vwtools 逐帧解帧 | 影响部分高级分析 |
| faster-whisper | 语音转写 | 没有字幕信息 |

> ⚠️ Pillow 是动图的硬依赖。装的时候如果直连 PyPI 超时，用镜像：
> ```
> python -m pip install pillow -i https://pypi.tuna.tsinghua.edu.cn/simple
> ```

## vw.py 在哪

**不用管，已经随包带上了。**

技能按这个顺序找：

1. 设置里的「vw.py 路径」（填了就只用这个，平时留空）
2. **`vendor/vw.py`** ← 随包携带的那份，装好就能用
3. 技能根目录的 `vw.py`（你要是喜欢直接丢在根目录也行）
4. `C:\Users\Public\video-watch\vw.py`
5. `~/video-watch/vw.py`
6. `~/Downloads/video-watch-skill-main/vw.py`

第 2 条是**相对路径算出来的**，所以你的 QQ Agent 装在哪个盘、哪个目录都不影响。

判断是否就绪：`python vendor\vw.py doctor` 能跑出「必需项就绪」。

### vw.py 的出处

`vendor/vw.py` 和 `vendor/vwtools.py` 来自开源项目 **video-watch-skill**（作者 CFITSec），
采用 MIT 许可证，允许随包分发。原许可证保留在 `vendor/LICENSE`，请勿删除。

## 为什么放在 `skills/` 而不是 `plugins/`

因为"看哪段、看几格、看没看清"没有任何规则能提前写死。插件按固定条件触发、看不到画面、也不能自己决定再调一次；技能把工具交给模型，模型看了速览图才知道该不该放大哪一段。

## 提示词里写死了什么

`skill.json` 的 `prompt.sections` 里规定了模型的观看纪律：

- **只说你真的看到的**。速览是稀疏采样，两格之间的过程没看到，不能说"他慢慢站起来"，只能说"第 12 秒还坐着，第 16 秒已经站着"。
- 拿不准就再 zoom 一次，别猜。
- 动图是循环短动作，按真实时间轴展开，要看节奏就给多几帧。
- 不要为了显得厉害复述画面细节。人家问"这视频在讲啥"，就答在讲啥。
- 视频里如果有别人的隐私（身份证、聊天记录、车牌、住址），复述时不要念出来。

## 限制（写在代码里）

| 限制 | 值 | 为什么 |
|---|---|---|
| 单次处理总时长上限 | 10 分钟 | 更长的铺 25 格会看不出东西，也费 token |
| 单次 zoom 跨度上限 | 2 分钟 | 跨太大就退化成速览了 |
| 每轮最多处理次数 | 6 次 | 防止对着一条视频反复铺图烧钱 |

## 实现上的几个坑（改代码前先读）

### 0. 资源治理：别让它跑着跑着把磁盘吃满（2026-10-18）

这是**最容易被忽略、也最难排查**的一类问题。三个泄漏点，都修了。

#### 泄漏点 1：`video.watch` provider 从不清理工作目录 ⚠️ 最严重

调用方是核心 `VideoReader`。它拿到 `image` 路径后**只负责把图发给模型，不会删目录**。

原来的写法：

```javascript
return { ok: true, image: r.image, manifest: r.manifest, workDir: dir };
//                                                  ^^^^ 每次留下一个 core-*/ 目录
```

每个目录里有 25 张单帧 + 联络表 ≈ 3~5MB。实测跑了几次就攒了 **15.8MB / 105 个文件**。

长期跑会怎样：磁盘慢慢被吃满 → ffmpeg 写图失败 → 视频功能整体挂掉。
用户看到的只是「最近怎么老是抽帧失败」，根本想不到是磁盘满了。

**修法**：把图读成 base64 一起返回，调用方不需要再碰磁盘，目录当场删掉。

```javascript
const buf = fs.readFileSync(r.image);
const sheet = `data:image/png;base64,${buf.toString('base64')}`;
cleanup(dir, c.keepWorkFiles);
return { ok: true, image: r.image, sheet, manifest: r.manifest,
         workDir: c.keepWorkFiles ? dir : '' };
```

代价是 base64 占一瞬间内存（140KB 图 ≈ 190KB 字符串），比留一堆文件划算太多。

**验证**：调用前后工作目录占用都是 0 KB。

#### 泄漏点 2：没有任何磁盘配额

实测工作目录攒到 105 个文件时才发现——没有任何代码在管总量。

**修法**：三层配额，挂在「新建工作目录」这个必然事件上（不开定时器，零成本）：

```javascript
const DISK_QUOTA_MB = 300;        // 超过就清理
const DISK_KEEP_RATIO = 0.7;      // 删到 70%，避免每条消息都清理
const ORPHAN_MAX_AGE_MS = 3600e3; // 超 1 小时的孤儿目录无条件删
```

`jobDir()` 里第一件事就是 `enforceDiskQuota()`：

1. 超龄孤儿目录（进程被杀留下的）→ 无条件删
2. 总量超配额 → 按「最久未修改」删到 70%
3. `_view/` 排在最后才动（里面是已交给模型的图，可能还有人看）

**实测**（把阈值调成 10MB 验证）：

```
清理前: 55.79 MB / 25 个目录
清理后:  6.85 MB /  4 个目录   ← 保留了最新的 3 个 + _view
```

#### 泄漏点 3：抽帧没有体积闸门

高复杂度画面（满屏噪点、细密纹理）在 `-q:v 4` 下能到 200KB+。
12 帧 = 2.4MB 原始 → **3.2MB base64 字符串**，HTTP body 直接顶到网关拒绝的尺寸。

用户看到的现象是「发了视频机器人就不理我了」——其实是 400。

**修法**：两道闸门。

```javascript
const FRAME_MAX_BYTES = 150 * 1024;       // 单帧超了就原地重压（q:v 8 + 缩到 512px）
const FRAMES_TOTAL_MAX_BYTES = 1400 * 1024; // 总量超了就提前收工，剩下的帧不要
```

**实测**（210MB 满屏随机噪点，最坏情况）：

```
帧数: 10（要 12，触发总量闸门提前收工）
单帧最大: 46 KB
总计: 0.45 MB
```

对比未加闸门时单帧能到 200KB+，现在被死死摁在 46KB。

### 1. 真实故障复盘：角色说"只拿到个壳子"

**2026-10-18 22:42**，群里发的 30 秒竖屏视频（480×852），角色回复"抽帧的组件没跑起来，只拿到个壳子"。

查下来是**两层原因叠加**：

**第一层：能力名对不上。**
核心只查 `video.frames`，而技能最初只提供了 `video.watch`。核心查不到 → `framesOk=false` → 降级成只给元信息。

**第二层：文件根本没下载下来。**
`VideoReader.#localize()` 有两条路，都失败了：

```
路径1：onebot.call('get_video'/'get_file')  → QQ 无缓存
路径2：下载 media.url                        → QQ 媒体链接带时效签名，核心的
                                              safe-fetch 偏保守，403/超时
```

于是 `hasFile=false`，后面所有步骤全部跳过。

**怎么验证的**（别只看技能"加载成功"就以为好了）：

```javascript
// 光看 route 判定不够，要看 probe 的最终 note
const out = await new VideoReader(null).probe({ path: '...' });
console.log(out.route, out.frames?.length, out.note);
```

修复前：`route: 'meta', frames: undefined, note: "无法获取视频文件…"`
修复后：`route: 'frames', frames: 12, note: "视频信息：时长 30.0 秒，480×852，12.4MB。已从中抽取 12 张画面截图…"`

**教训**：技能"加载成功"≠"功能可用"。必须查到 `implementedCapabilities` 里有没有核心要的那个能力名，再跑一次真实的 `probe` 看帧数。

### 1. 工具必须注册在 `setup(api)` 里

加载器只调用 `setup(api)`（旧入口 `register(api)` 也认，但只认这两个名字）。

我一开始把注册逻辑写在单独导出的 `register(api)` 里、`setup` 只存配置，结果：

```
⚠️ video-watch 在 skills/（LLM 型）却没有注册任何工具：模型看不到它
```

技能列表里 `toolIds` 是 0，模型完全不知道有这个能力。

### 2. 图片会在模型看到之前被删掉

早期写法是"生成图 → 立刻 cleanup 工作目录 → 返回图片路径"，结果模型拿到一个**不存在的路径**，等于什么都没看到。

正确顺序（`keepImage` 就是干这个的）：

```
生成图 → 复制到 data/video-watch/_view/ → 删工作目录 → 返回保留后的路径
```

### 3. 动图和视频的 manifest 结构不一样

| | grid（视频） | gif（动图） |
|---|---|---|
| 行数 | `rows` | **没有**，要从 `row` 最大值推 |
| 格子编号 | `index` | **没有**，用数组序号 |
| 间隔 | `step_s` | **没有**，用相邻 `t` 的差 |
| 图片名 | `grid.png` | `gif_sheet_01.png` |

早先只按 grid 写，动图就输出「3 列 × undefined 行」。

### 4. `manifest.t1` 不能当作"这段的覆盖范围"

vw.py 指定 `--t0/--t1` 取段时，`t1` 仍写**整片时长**。于是 zoom 第 20~28 秒会被描述成"覆盖 0.0~28.0 秒"——把"片尾"当成了"这段的结尾"，模型会据此说错时间。

真正的范围只能从第一格到最后一格算。

### 5. `available()` 必须是同步函数

SkillManager 的可用性判定是同步调用链，返回 Promise 会被当成"可用"（Promise 是 truthy）。所以：首次乐观放行 + 后台探测 + 结果缓存。

## 排障

| 现象 | 原因 | 怎么修 |
|---|---|---|
| 报「没找到 python」 | PATH 里没有 | 在设置里填 python 完整路径 |
| 报「没找到 vw.py」 | 位置不对 | 在设置里填 vw.py 完整路径 |
| 报「gif 需要 Pillow」 | 没装 Pillow | `python -m pip install pillow -i https://pypi.tuna.tsinghua.edu.cn/simple` |
| 图版上帧号看不清 | 字体没生效 | 跑 `python vw.py doctor` 看 font 那行是否「生效」 |
| 报缺滤镜 | ffmpeg 是精简版 | 换 Gyan 完整构建：`winget install Gyan.FFmpeg` |
| 模型说"看不清" | 单格太小 | 让它用 `zoom` 放大那一段 |
| 铺图很慢 | 视频很长或分辨率很高 | 正常；用 zoom 分段看比全片铺格更快 |
